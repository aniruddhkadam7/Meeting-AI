1 · Audio capture — WASAPI loopback

20 ms buffer requested (system_capture.rs:70). audio_probe (existing tool) reports discontinuities and delivery ratio in real time; the architecture here was already hardened in an earlier pass — WASAPI delivers zero packets while the render endpoint is idle, which is why SilenceGapFiller exists. Not revisited: no evidence of a problem, and the fix is orthogonal to CPU class.

2 · Buffering — SilenceGapFiller

Pure arithmetic against a monotonic clock, one Vec<f32> allocation only when a real gap (>120 ms) is detected. Negligible cost on any CPU class.

3 · Resample / format conversion

Every ~20 ms WASAPI packet (typically 48kHz stereo → 16kHz mono) currently costs 3–4 heap allocations: one in downmix_to_mono (allocates even when channels ≤ 1), one for the resampler's leftover.drain() block, one for its output Vec. At ~50 packets/second during speech, that's 150–200 allocations/sec. Trivial on the reference machine's L2/L3 cache and memory bandwidth; proportionally more expensive on an i3's smaller cache and often slower/single-channel RAM — but still two orders of magnitude below the ~400 ms inference cost. Real, worth removing, not the bottleneck.

4 · VAD / endpointing

Architectural finding

There is no separate VAD stage gating inference. sidecar.py's worker loop calls recognizer.decode_stream() unconditionally on every audio chunk that arrives (sidecar.py:222–225) — silence and speech both reach the model. Endpointing (is_endpoint, rules 1–3) runs after decoding, to decide when to finalize, not whether to decode at all. This is priority item D in the brief, and it's real: every silent packet still pays a forward pass.

5 · STT chunk formation

No app-level chunking layer exists — whatever WASAPI hands over per packet goes straight to sidecar.send_samples(). The sherpa-onnx streaming model has its own internal frame/chunk semantics (80 ms lookahead, baked into the exported model); WhitedotAI doesn't batch multiple WASAPI packets before sending. This is priority item C's actual target — but chunk size here means "how often do we call into the decoder," which is downstream of finding D.

6 · Model inference — where the time actually goes

The bottleneck

Every latency number in this report — first-partial (~490 ms), finalize (~360–400 ms) — is dominated by the forward pass through the NeMo FastConformer encoder/decoder/joiner, not by anything upstream. Detailed evidence in §3.

7–8 · First partial / final result

Both are direct, unbuffered emissions the instant the decoder produces a hypothesis (sidecar.py:235–239) or an endpoint fires (sidecar.py:227–232). No queueing delay, no batching delay. Their latency is stage 6's latency plus a few milliseconds of JSON serialization over stdout.

9 · UI delivery

Sidecar → Rust reader thread → crossbeam channel → Tauri event → React re-render. Entirely event-driven, no polling, no artificial delay. Not measured in isolation this pass (no reason to suspect it — the architecture has no batching or timer anywhere in this leg), and not where an i3 would feel slow.

03 The bottleneck, stated precisely

Two independent lines of evidence, both already in docs/stt-benchmark.md and this pass's new sweep, point at the same place.

Latency moves by single-digit milliseconds — noise — across a 4× change in thread count, while CPU cost scales almost linearly. If threads were the bottleneck, 1 thread would be dramatically slower than 4. It isn't. The ~350–500 ms figure is a near-fixed cost: the encoder/decoder/joiner forward pass over the model's exported 80 ms chunk size, plus greedy-search decode overhead — work that doesn't parallelize across more ONNX threads because the computation graph for one streaming chunk is inherently sequential (encoder → decoder → joiner, in that order, per frame).

Confirmed, not assumed

This directly satisfies the brief's instruction not to "simply reduce STT threads and call the problem solved" — the data shows reducing threads doesn't cost latency, but it also doesn't buy any. The win from fewer threads is CPU headroom, not speed. That headroom is real and useful (see §5, items E–F) — it just isn't a latency fix on its own.

04 Low-end simulation method — and where it broke

No real i3 hardware was available. Two simulation approaches were attempted; only one produced trustworthy numbers. Reporting the failure is part of the finding.

Approach 1 — ONNX thread-count capping (valid)

STT_NUM_THREADS genuinely constrains ONNX Runtime's own internal thread pool — this is the mechanism the shipped app already uses, so capping it is a faithful simulation of "a CPU with fewer execution units available to the model," even on fast host hardware. All thread-count numbers in this report use this method.

Approach 2 — Windows process-affinity masking (attempted, unreliable — do not trust)

To simulate genuine OS-level core scarcity (not just ONNX's thread pool), the benchmark's Python process was launched and its ProcessorAffinity pinned externally to 4 and then 2 logical processors via .NET's System.Diagnostics.Process, mimicking a 4c/4t or 2c/4t i3.

PID=24060 affinity=3        ← set successfully, immediately after
t=300ms  affinity=65535     ← reverted to all 16 logical processors
t=600ms  affinity=65535     ← stayed reverted for the rest of the run
Root cause found

numpy/_core/__init__.py sets OPENBLAS_MAIN_FREE=1 on import, specifically to undo OpenBLAS's own default of pinning the process to one core. The side effect observed here: it also silently discards any externally applied affinity mask, snapping the process back to all cores within one sampling interval. This is documented numpy/OpenBLAS behavior, not a scripting mistake — but it means affinity-based simulation does not hold for this dependency stack (sherpa-onnx → onnxruntime → numpy).

Consequence: every "i3" number in this report comes from Approach 1 (thread-count capping) only. No number in this report should be read as "measured with genuinely fewer CPU cores available" — that would need real hardware, or a lower-level mechanism (a Windows Job Object CPU-rate limit applied before the Python interpreter starts, not attempted this pass).

05 Candidate optimizations, benchmarked or reasoned through

In the priority order given. Each carries a verdict — recommend, investigate further, defer, or reject — based on what was actually measured, not assumed.

A

Keep the model warm

Already true. Model loads once at sidecar startup (~1.2–1.3 s, paid once per recording session) and is reused for the process lifetime; between utterances only recognizer.reset(stream) runs — a cheap state clear, not a reload. Nothing to change.

Already done
B

Reduce buffering copies/allocations

3–4 heap allocations per ~20 ms audio packet in resample.rs, confirmed by code read (§2.3). Real cost, disproportionately worse on an i3-class cache/memory subsystem, but two orders of magnitude below the inference cost — won't move first-partial/final numbers on its own.

Worth doing, won't fix latency alone
C

Optimize chunk size

The model's chunk size (80 ms) is baked into the exported ONNX graph — not a runtime parameter. The only "chunk size" WhitedotAI controls is how often WASAPI packets are forwarded, which is already immediate (no app-level batching delay exists to remove).

No app-level lever exists
D

VAD should skip inference during silence

Confirmed gap (§2.4): every chunk decodes, silent or not. A pre-inference energy gate could cut wasted forward passes during dead air — real CPU savings on a constrained core count. Not yet benchmarked; needs a prototype before claiming a number.

Real gap — needs a prototype
E

Give STT scheduling priority

No process/thread priority control exists anywhere in the codebase today (confirmed by search — zero hits for Windows priority-class APIs). A real gap on a 2–4 core machine where the OS scheduler has much less slack to hide contention.

Real gap — unimplemented
F

Throttle RAG indexing during active STT

Confirmed: RAG document upload/indexing is fully synchronous and blocks the single uvicorn worker (from Milestone 4a's investigation) — it can run concurrently with STT today with zero coordination between the two processes. The only other periodic background work is a 60 s analytics flush (network I/O, not CPU-bound) — so this item's real target is narrow and specific: RAG indexing only.

Confirmed gap, narrow fix
G

Faster runtime / quantization options

Model is already int8-quantized (confirmed file naming + docs/stt-benchmark.md). No fp32 variant exists to compare down from. A different runtime (e.g. whisper.cpp with more aggressive quantization) was already evaluated in the original engine bake-off and rejected for accuracy/latency reasons — re-litigating that choice is out of scope for this profiling pass per the "do not change STT model" instruction.

Already decided; out of scope here
H

Hardware acceleration

Checked and previously rejected: the installed sherpa_onnx wheel is CPU-only (not sherpa-onnx-gpu), and an i3 machine is exactly the profile least likely to carry a discrete GPU. Not revisited.

No GPU to accelerate on
I

Benchmark 1 / 2 / 4 threads, don't assume

Done — this is §3's core measurement. Result: thread count is a CPU-cost knob, not a latency knob, confirmed on this pass and consistent with Milestone 4a.

Done — see §3

07 Recommended changes — profiling-phase conclusion

Per the brief: this is where the report stops. No STT architecture or model change ships from this pass without a follow-up decision.

  1. Do not touch thread count as a latency fix. The data closes this question — it was already closed in Milestone 4a and this pass reconfirms it independently.
  2. Prototype VAD-gated inference (item D) — skip decode_stream() calls on chunks the endpointer's own silence detection would reject anyway. This is the most promising untried lever: it targets stage 6 (the actual bottleneck) by reducing how often the expensive forward pass runs, not by trying to make each pass faster.
  3. Implement RAG-vs-STT scheduling coordination (item F) — pause or de-prioritize document indexing while an STT session is active. Narrow, confirmed gap, low implementation risk since the two already run as separate processes.
  4. Investigate STT process priority (item E) — Windows SetPriorityClass/THREAD_PRIORITY_TIME_CRITICAL on the sidecar process, gated to low-tier hardware only. Needs a benchmark before shipping — priority boosting can starve the OS/UI thread if misapplied.
  5. Fix the allocation churn in resample.rs (item B) as a low-risk, always-safe cleanup — reuse buffers across calls instead of allocating per packet. Won't move the headline latency numbers; will reduce GC/allocator pressure that matters more on constrained RAM.
  6. Do not pursue G or H without new information — both were evaluated and closed by prior work or by this machine's own hardware profile.

09 CPU / RAM / accuracy impact of what's recommended

If items D + F + E ship (pending their own benchmarks)

  • CPU: lower average load during silence-heavy sessions (D); no CPU contention spikes from concurrent indexing (F); STT gets scheduler priority under contention (E) — net effect should be fewer stutters, not necessarily a lower peak.
  • RAM: unaffected by D/E/F. Item B (allocation cleanup) reduces allocator churn, not steady-state RSS.
  • Accuracy: zero impact expected from D/E/F/B — none touch the model, VAD thresholds, or endpointing rules. A VAD-gate prototype (D) would need an explicit regression test proving WER is unchanged before shipping, per the brief's own requirement.
